스레드는 프로세스 안에서 실행되는 흐름이다. 각 스레드는 자신의 레지스터 상태와 스택을 가지지만, 같은 프로세스의 주소 공간과 파일 디스크립터 등을 공유한다. **실행 흐름이 나뉘어 있다는 것과 장애가 격리된다는 것은 다르다.** [Linux pthreads 설명](https://man7.org/linux/man-pages/man7/pthreads.7.html)

## 무엇을 공유하고 무엇을 따로 가지는가

| 대상 | 같은 프로세스의 스레드 사이에서 |
| --- | --- |
| 코드와 전역 데이터, 힙 | 공유 |
| 열린 파일 디스크립터 | 공유 |
| 실행 위치와 레지스터 상태 | 스레드별 관리 |
| 스택 | 스레드별 할당, 같은 주소 공간 안에 존재 |

스택을 따로 가진다고 다른 스레드가 그 주소에 접근할 수 없는 것은 아니다. 스택의 객체를 가리키는 포인터를 넘겼다면 수명과 동기화를 함께 관리해야 한다.

## 스레드를 늘리면 언제 도움이 될까

I/O를 기다리는 작업이 많다면 한 작업의 대기 시간에 다른 작업을 진행할 수 있다. 계산을 독립적으로 나눌 수 있고 CPU 여유가 있다면 병렬 처리도 가능하다.

반대로 모든 작업이 같은 락을 기다리거나 CPU를 이미 다 쓰고 있다면 스레드만 늘려도 처리량이 늘지 않는다. 문맥 전환과 동기화 비용이 더 커질 수 있다. “스레드가 가볍다”는 비교만으로 성능을 판단하기 어려운 이유다.

## 공유 메모리에는 동기화가 필요하다

두 스레드가 같은 값을 동시에 읽고 수정하면 갱신 하나가 사라질 수 있다. 뮤텍스나 원자적 연산으로 보호해야 하는 것은 개별 줄보다 **함께 유지해야 하는 상태의 관계**다.

락을 여러 개 사용한다면 획득 순서도 정해야 한다. 한 스레드가 A를 잡고 B를 기다리는 동안 다른 스레드가 B를 잡고 A를 기다리면 교착 상태가 된다.

## 멀티스레드와 멀티프로세스

| 기준 | 멀티스레드 | 멀티프로세스 |
| --- | --- | --- |
| 주소 공간 | 같은 프로세스 안에서 공유 | 기본적으로 분리 |
| 데이터 전달 | 공유 메모리와 동기화 | IPC, 소켓, 명시적인 공유 메모리 등 |
| 장애 경계 | 메모리 손상이나 치명적 오류가 프로세스 전체에 영향 | 프로세스 단위 격리 가능 |
| 비용 | 스택, 스케줄링, 동기화 비용 | 별도 주소 공간과 통신 비용 등 |

프로세스를 나누어도 공용 DB, 파일, CPU와 메모리를 함께 쓰면 서로 영향을 줄 수 있다. 프로세스 분리는 모든 의존성을 없애 주는 장치가 아니다.

## 실무에서 다시 만난 문제

[파서 취소와 자원 소유권](/posts/parser-cancellation-resource-ownership/)에서는 요청이 취소된 뒤에도 실행 중인 작업이 자원을 사용할 수 있었다. 호출자가 기다리기를 멈췄다는 사실만으로 실제 작업의 종료를 판단해서는 안 된다.

새 병렬 작업을 설계할 때는 “이 작업이 끝났다는 것을 누가 확인하고, 그 전에 공유 자원을 해제할 수 있는가?”를 확인해 보자. 스레드의 생성 방법보다 이 수명 경계가 버그를 찾는 데 더 도움이 된다.
