팀장으로 승급했는데 일부 공유 리소스에 접근하지 못하는 문제가 있었다. 권한 부여 중 하나가 실패해도 멤버 문서의 역할 변경을 계속 진행했기 때문이다. 화면에는 팀장으로 보이지만 실제 권한은 그 상태와 일치하지 않았다.

여러 MongoDB 변경을 한 트랜잭션에 묶는 것이 첫 번째 해결이었다. 이후에는 트랜잭션에 **어떤 데이터를 포함해야 하는가**가 더 중요해졌다.

> 2026-09-29 보완: 기존 글의 “사용자 역할 동기화는 백그라운드로 처리해도 된다”는 설명을 수정했다. 권한 판단에 쓰이는 역할 사본은 단순한 후처리가 아니다.

## 역할 변경의 성공 조건부터 정한다

예를 들어 팀 멤버 문서와 사용자 문서의 `org_roles`를 서로 다른 경로가 읽는다면 한쪽만 갱신한 상태는 완료가 아니다. 같은 역할을 두 곳에서 읽는 순간 두 표현의 정합성도 계약에 들어간다.

| 데이터·작업 | 성공 조건과의 관계 |
| --- | --- |
| 멤버의 소속·역할 | 변경의 기준 상태 |
| 권한 판단에 쓰는 역할 projection | 기준 상태와 일치해야 함 |
| 권한 부여·회수 | 같은 변경의 실패를 함께 처리해야 함 |
| 사용자에게 보내는 알림 | 커밋된 결과를 바탕으로 전달 |
| 권한 캐시 | 오래된 권한으로 허용하지 않도록 별도 무효화·차단 필요 |

캐시나 외부 서비스가 MongoDB 트랜잭션에 자동으로 참여하는 것은 아니다. 같은 세션 컨텍스트를 전달한 MongoDB 작업과 외부 부수 효과를 구분해야 한다. [MongoDB 트랜잭션](https://www.mongodb.com/docs/manual/core/transactions/)

## 콜백에 넣었다고 실패가 자동 전파되지는 않는다

트랜잭션 콜백 안에서 권한 회수 함수의 오류를 무시하고 `nil`을 반환하면, 필요한 변경이 빠져도 커밋을 시도할 수 있다. 각 필수 작업의 오류를 확인해 호출자에게 반환해야 한다.

기존 예시에는 일부 오류 확인이 생략되어 있었다. 해당 코드를 완성된 권한 변경 구현으로 오해하지 않도록 제거하고, 실제로 유지해야 하는 조건을 남겼다.

1. 변경 전 소속과 역할을 확인한다.
2. 멤버 상태, 필수 권한, 권한에 쓰이는 projection을 같은 커밋 범위에 포함한다.
3. 하나라도 실패하면 오류를 반환하고 해당 변경을 롤백한다.
4. 커밋 이후 캐시와 알림을 처리하되, 실패를 추적할 수 있게 한다.

이는 모든 시스템에 똑같은 테이블 구성을 요구하는 절차가 아니다. 이 사례처럼 같은 MongoDB 안에 함께 갱신해야 할 상태가 있는 경우의 기준이다.

## 백그라운드 작업으로 넘길 수 있는가

“느리니 고루틴으로 보낸다”보다 먼저, 그 작업이 실패한 상태에서도 API가 성공했다고 답할 수 있는지 묻는다. 감사 알림과 관리자 권한 회수는 같은 종류의 후처리가 아니다.

서로 다른 저장소 때문에 한 트랜잭션에 묶을 수 없다면 적용 중 상태, 오래된 권한 사용 차단, 내구성 있는 재시도와 조정 절차가 필요하다. 로그만 남기는 고루틴은 서버 종료 뒤 복구할 작업을 보존하지 않는다.

## 최근 작업에서 확인한 경계

[멤버십과 역할 projection을 함께 커밋한 사례](/posts/membership-projection-atomic-commit/)에서는 변경 원본뿐 아니라 권한 검사에 쓰이는 사본까지 확인했다. API 응답이 성공한 것과 두 저장 표현이 일치하는 것은 각각 관찰해야 한다.

검증도 같은 경계를 따른다. 권한 갱신 중간에 실패를 주입한 뒤 멤버 문서와 역할 projection이 함께 이전 상태를 유지하는지, 강등 직후 옛 캐시로 관리자 요청이 허용되지 않는지 확인한다. 이것이 “트랜잭션을 사용했다”보다 구체적인 완료 증거다.
