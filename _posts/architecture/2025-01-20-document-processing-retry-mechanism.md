문서 처리 중 잠깐의 네트워크 장애가 나도 곧바로 업로드 실패 알림을 보냈다. 다시 올리면 성공할 수 있는 요청까지 사용자가 직접 반복해야 했다. 그래서 파이프라인의 실패 단계에서 재시도하는 흐름을 추가했다.

하지만 “에러면 이전 단계 이벤트를 다시 발행한다”만으로는 부족했다. 같은 입력으로 성공할 가능성이 있는지, 어느 버전을 다시 처리하는지, 이미 저장된 결과가 있는지를 함께 확인해야 한다.

## 단계 이름은 재시도 가능 여부를 말해 주지 않는다

| 실패 원인 | 판단 |
| --- | --- |
| 일시적인 네트워크 오류·서비스 과부하 | 시간·횟수 제한 안에서 재시도 검토 |
| 손상된 문서·지원하지 않는 형식 | 같은 입력을 반복해도 해결되지 않을 수 있음 |
| 필수 식별자나 메시지 형식 오류 | 정상 작업에서 분리하고 원인 기록 |
| 쓰기 요청 뒤 응답만 유실 | 실패로 단정하지 말고 결과·멱등성 확인 |
| 오래된 처리 시도의 결과 | 현재 시도에 적용하지 않도록 식별자 검사 |

`ParsingError`라는 이름만으로 일시적 오류라고 분류할 수 없다. [잘못된 메시지가 파티션을 막은 사례](/posts/kafka-poison-partition-and-commit-frontier/)처럼 영구적인 입력 오류를 반복하면 뒤의 정상 작업도 지연된다.

## 재개할 단계와 재사용할 산출물을 함께 정한다

기존 파이프라인에서는 아래 이벤트로 다음 단계의 처리를 다시 요청했다.

| 실패 단계 | 재발행에 사용한 이전 이벤트 | 함께 확인할 것 |
| --- | --- | --- |
| Parsing | `FileUploaded` | 같은 원본 객체 버전인가 |
| Chunking | `DocumentParsingCompleted` | 파싱 산출물이 여전히 유효한가 |
| Embedding | `DocumentChunkingCompleted` | 청크 버전과 임베딩 설정이 일치하는가 |
| Store | `DocumentEmbeddingCompleted` | 같은 임베딩 결과와 쓰기 시도인가 |

이것은 당시의 이벤트 계약이다. 다른 서비스에서 이름만 같게 발행한다고 안전한 재시도가 되는 것은 아니다. 식별자, 객체 위치, 버전과 처리 시도를 보존해야 한다. [RAG 파이프라인에서 버전을 유지하는 방법](/posts/immutable-versions-through-rag-pipeline/)

## 재시도 상태를 잃지 않는 순서

기존 예시는 Redis 조회 오류와 “아직 상태가 없음”을 같은 분기로 처리했다. 저장소 장애 때문에 읽지 못한 것을 첫 시도로 판단하면 재시도 횟수가 초기화될 수 있다. 조회 실패와 미존재를 구분해야 한다.

횟수 증가와 다음 실행 예약도 함께 검토한다. 두 워커가 같은 횟수를 읽고 각각 재발행할 수 있고, 상태만 저장한 뒤 발행 전에 종료될 수도 있다. 원자적인 상태 전이와 복구 가능한 발행 기록이 필요한 이유다.

최종 실패를 DB에 저장하지 못했다면 Redis의 유일한 추적 기록을 먼저 지우지 않는다. 실패 기록·재시도 예약·알림은 각각 성공 여부를 확인하고 복구할 수 있어야 한다. 기존 글의 오류를 생략한 코드는 이 계약을 충족하지 못해 제거했다.

## 재시도는 새 시도와 구분한다

파일 ID와 단계 이름만으로 상태를 저장하면 같은 파일의 재업로드나 재처리 결과가 섞일 수 있다. 원본 버전과 처리 시도를 식별하고, 늦게 도착한 이전 이벤트가 현재 상태를 덮지 못하게 한다.

입력 메시지를 다시 소비할 수 있다는 이유만으로 외부 쓰기가 안전해지지는 않는다. Kafka의 소비 위치와 외부 저장 결과는 별도 경계다. [Kafka 전달 의미](https://kafka.apache.org/41/design/design/#message-delivery-semantics)

## 즉시 재시도는 제한된 선택이다

단발성 오류를 빠르게 회복할 수도 있지만 과부하가 지속되면 같은 요청을 즉시 다시 넣는 것이 부하를 키운다. 재시도 가능 오류에만 적용하고 전체 시간, 횟수, 대기 간격과 동시 실행 수를 함께 제한한다.

사용자에게는 복구 가능한 일시적 실패마다 최종 실패 알림을 보낼 필요가 없다. 대신 처리 중 상태와 최종 결과를 구분한다. 입력 수정이나 권한 변경이 필요한 실패까지 숨기며 기다리게 해서는 안 된다.

처리 중 목록을 조회할 때도 전체 Redis 키 공간을 `KEYS`로 훑는 예시는 사용하지 않는다. `KEYS`는 키 수에 비례하는 작업이므로 요청 경로에는 사용자별 상태 인덱스 등 조회 범위가 제한된 구조가 필요하다. [Redis KEYS](https://redis.io/docs/latest/commands/keys/)

## 확인할 실패 지점

재발행 직전과 직후, 외부 저장 직후와 완료 기록 직전에 프로세스를 멈춰 보자. 재시작 후 같은 버전을 이어 처리하고, 횟수를 잃지 않으며, 새 시도의 결과를 훼손하지 않아야 한다. 알림이 줄었다는 수치만으로는 이 복구 계약을 검증할 수 없다.
