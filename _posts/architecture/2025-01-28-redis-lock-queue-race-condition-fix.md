두 워커가 큐에서 같은 작업을 실행했다면, Redis 명령이 원자적이지 않은 것일까. **명령 하나의 원자성과 여러 명령으로 만든 절차의 원자성은 다르다.** 이 차이를 가상의 큐와 두 워커로 살펴보자.

## 읽기와 삭제를 나누면 같은 요청을 가져갈 수 있다

리스트 끝의 값을 읽고 나중에 지우는 절차를 가정해 보자. 다음 순서가 가능하다.

```text
A: 마지막 항목 X 읽기
B: 마지막 항목 X 읽기
A: 읽은 항목을 제거하고 X 실행
B: 자신도 X 실행
```

워커 A와 B가 모두 읽기를 끝낸 뒤 삭제하면 둘 다 같은 요청을 실행할 수 있다. 실패 후 각각 다시 넣으면 재시도 요청도 늘어난다. Redis의 개별 명령이 원자적이라는 사실이 두 명령의 조합까지 원자적으로 만들지는 않는다.

## RPOP은 어디까지 보장할까

`RPOP`은 리스트 끝의 항목을 꺼내면서 제거한다. 동일한 리스트 항목을 여러 워커가 읽은 뒤 각각 삭제하는 경합을 없앨 수 있다. [RPOP](https://redis.io/docs/latest/commands/rpop/)

하지만 이것은 **중복 dequeue 방지**다. 꺼낸 직후 프로세스가 죽으면 리스트에는 항목이 없고 업무 처리는 끝나지 않았을 수 있다. 이미 중복된 항목을 큐에 넣었다면 그것도 별도 문제로 남는다.

유실을 허용할 수 없다면 대기 리스트에서 처리 중 리스트로 원자적으로 옮기고, 처리 성공 후 확인 기록을 남기는 방식이 필요하다. Redis의 `LMOVE` 문서도 처리 중 리스트와 확인·복구 절차를 사용하는 reliable queue 패턴을 설명한다. 시간 초과 뒤 재전달될 수 있으므로 처리 자체의 멱등성도 필요하다. [LMOVE의 reliable queue 패턴](https://redis.io/docs/latest/commands/lmove/#pattern-reliable-queue)

## 실패 큐를 없애는 것은 별개의 결정이다

실패 큐의 크기가 커졌다고 큐를 지우면 원인도 해결되는 것은 아니다. 실패 큐는 원래 처리하지 못한 작업을 분리해 둔 장소다.

실패 큐를 유지할지는 요청의 복구 계약으로 정한다. 만료된 임시 락 획득 요청처럼 폐기해도 되는 작업과, 저장해야 할 문서 작업을 구분해야 한다. 후자는 실패 이유, 재처리 여부와 보관 기간을 관리해야 한다. 로그만 남기고 버리면 작업을 복구할 근거가 사라질 수 있다.

[Kafka의 잘못된 메시지를 격리한 사례](/posts/kafka-poison-partition-and-commit-frontier/)도 같은 구분을 다룬다. 진행을 막는 메시지를 격리하는 것과 처리됐다고 간주하는 것은 다르다.

## 백프레셔도 원자성을 확인한다

큐 길이를 조회한 뒤 별도 호출로 추가하면 여러 생산자가 같은 빈자리를 보고 동시에 넣을 수 있다. 이 방식은 대략적인 제한이 될 수 있지만 엄격한 최대 길이를 보장하지는 않는다.

정확한 상한이 필요하면 길이 검사와 추가를 원자적으로 묶어야 한다. 여러 키를 쓰는 Redis Cluster 구성에서는 같은 슬롯 조건도 확인해야 한다. 요청 만료와 최대 재시도 횟수 역시 최종 실패를 어떻게 기록하고 호출자에게 알려 주는지까지 포함한다.

## 운영 정리는 처리 결과를 확인한 뒤 한다

큐에는 중복 요청과 아직 수행하지 않은 정상 요청이 섞여 있을 수 있다. 큐를 비우는 것만으로 정상 처리를 확인할 수 없다. 먼저 생산자·소비자의 동작을 통제하고, 요청 ID별 완료 여부와 복구 대상을 확인해야 한다.

검증할 때는 워커 둘을 동시에 실행하는 경우뿐 아니라 **꺼낸 직후 종료**, **처리 직후 확인 기록 전 종료**도 넣어 보자. 첫 번째는 유실 가능성을, 두 번째는 중복 실행에 대한 내성을 확인한다.
