사용 설명서를 새로 올렸는데 챗봇은 예전 절차를 안내한다. 검색 모델이 문장을 잘못 고른 것일까? 그럴 수도 있지만 먼저 더 단순한 문제를 살펴볼 필요가 있다. **새 원본과 검색 가능한 자료가 같은 버전인지**다.

여기서는 가상의 문서 검색 서비스를 생각한다. 원본을 파싱하고 문장을 청크로 나눈 뒤 임베딩을 만들어 검색한다. 답변에는 검색한 문장의 출처를 붙인다. 각 단계가 따로 실행된다면 파일을 교체한 순간 모든 파생 자료가 함께 바뀌지는 않는다.

## 파일의 이름과 내용은 같은 식별자가 아니다

`manual.pdf`라는 경로는 그대로여도 그 안의 바이트는 달라질 수 있다. 오래 걸리는 파싱 작업이 경로만 기억한다면, 작업을 시작할 때와 실제로 읽을 때 서로 다른 내용을 볼 수 있다.

이를 피하는 한 방법은 처리 대상 원본을 불변 버전으로 지정하는 것이다. 원본 버전은 “어떤 내용인가”에 답한다. 처리 시도는 “그 내용을 몇 번째로 처리하는가”에 답한다. 같은 원본의 임베딩이 실패해 다시 실행됐다고 문서 내용까지 바뀐 것은 아니다.

객체 저장소의 버전 관리도 도움이 된다. 예를 들어 S3는 같은 키 아래 여러 객체 버전을 보관할 수 있다. 다만 저장소의 version ID와 애플리케이션이 사용자에게 보여 주는 문서 버전은 별도의 값일 수 있다. 어느 값을 실제 다운로드에 사용할지 연결해 두어야 한다. [S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)

## 임베딩에도 출처가 필요하다

벡터만으로는 그 값이 어느 원본에서 나왔는지 알기 어렵다. 검색할 수 있도록 저장한 자료에는 원본을 다시 찾을 수 있는 연결이 필요하다. 청크를 다른 길이로 나누거나 임베딩 모델을 바꾸는 경우도 생각해 보자. 원본은 같아도 파생 색인은 달라질 수 있다.

따라서 원본의 정체성과 색인을 만든 설정을 구분하면 재처리를 설명하기 쉬워진다. 모든 시스템이 같은 필드 구성을 가져야 한다는 뜻은 아니다. “이 검색 결과를 만들 때 읽은 원본을 다시 열 수 있는가?”라는 질문에 답할 정보가 필요하다는 뜻이다.

내용 해시로 바이트의 일치를 확인할 수도 있다. 다만 신뢰하지 못하는 발행자가 파일과 해시를 함께 바꾸면 둘은 여전히 일치한다. 해시는 출처의 신뢰나 읽기 권한을 대신하지 않는다.

## 여러 문서를 고르면 조합까지 보존한다

문서 A의 버전 2와 문서 B의 버전 7만 검색한다고 하자. 문서 ID가 A 또는 B인지, 버전이 2 또는 7인지만 따로 검사하면 A의 버전 7도 통과한다. 각 문서와 그 버전을 한 쌍으로 비교해야 한다.

아래는 Python 표준 타입만 사용하는 작은 검사다. 실제 벡터 DB나 검색 서비스의 구현은 아니다.

```python
requested = {("manual-a", 2), ("manual-b", 7)}
hits = [("manual-a", 2), ("manual-b", 7)]
wrong = ("manual-a", 7)

# 값을 따로 모으면 요청하지 않은 조합도 통과한다.
ids = {doc for doc, version in requested}
versions = {version for doc, version in requested}
assert wrong[0] in ids and wrong[1] in versions

# 요청한 조합 전체를 비교한다.
assert all(hit in requested for hit in hits)
assert wrong not in requested
print("document-version pairs preserved")
```

DB 필터에서도 같은 논리가 필요하다. 한 문서의 ID와 버전은 AND로 묶고, 그렇게 완성한 대상들을 OR로 연결한다. 이 예제는 조합의 의미만 확인한다. 접근 권한, 누락 필드, DB 쿼리의 동작은 별도로 검사해야 한다.

## 새 버전이 아직 검색되지 않는다면

새 원본은 저장됐지만 색인은 준비되지 않은 시간이 생긴다. 이때의 표시와 검색 정책에는 선택지가 있다.

| 선택 | 얻는 것 | 설명해야 할 비용 |
| --- | --- | --- |
| 준비된 이전 버전을 계속 제공 | 검색을 계속할 수 있음 | 어떤 버전인지 분명히 표시해야 함 |
| 새 버전 준비까지 검색에서 제외 | 최신 원본과 다른 근거 사용 방지 | 일시적으로 결과가 줄어듦 |
| 새 색인 준비 후 공개 버전을 전환 | 원본과 색인 전환을 맞추기 쉬움 | 준비·전환 상태 관리 필요 |

어느 정책이든 이전 버전을 새 버전인 것처럼 보이면 안 된다. 준비 상태와 최신 파일의 존재를 하나의 `완료` 값으로 합치면 이 차이를 표현하기 어렵다.

또한 색인에 쓴 직후 바로 조회되는지는 저장소의 일관성 설정에 달려 있다. Milvus도 여러 consistency level을 구분한다. 애플리케이션이 기대하는 “검색 준비 완료”의 시점은 선택한 읽기 설정과 함께 검증해야 한다. [Milvus Consistency](https://milvus.io/docs/consistency.md)

## 인용 링크를 열 때도 버전은 이어진다

답변을 저장할 때 파일명만 남기면, 나중에 링크를 열었을 때 새 문서가 나타날 수 있다. 그 답변의 근거를 확인하려던 사용자는 다른 내용을 보게 된다. 인용은 당시 검색한 원본 버전으로 이어져야 한다.

과거 버전을 가리킨다는 사실이 현재 읽을 권한까지 주지는 않는다. 링크를 열 때의 접근 권한은 다시 확인한다. 오래된 문서를 보관하지 않는 정책이라면, 다른 버전으로 조용히 대체하기보다 해당 근거를 더 이상 열 수 없다고 표시하는 편이 정직하다.

검사는 모델의 답변 문장보다 먼저 할 수 있다. 두 버전의 내용을 확연히 다르게 만들고 옛 파싱 결과를 늦게 도착시켜 보자. 검색 결과와 인용이 어떤 원본을 가리키는지 끝까지 따라갈 수 있다면, 그다음에 검색 품질을 평가할 기준도 생긴다.
