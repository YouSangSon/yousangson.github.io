파일을 `io.Reader`로 넘기면 메모리를 조금씩만 쓸까. 호출하는 코드가 파일 전체를 읽지 않더라도, 데이터를 받는 SDK는 전송용 버퍼를 먼저 만들 수 있다. **스트리밍은 데이터를 전달하는 방식이고, 메모리 상한은 각 단계의 할당 방식으로 정해진다.**

이 글은 Go 1.24.5와 공개된 minio-go v7.0.97 소스를 기준으로 그 차이를 살펴본다. 실제 서비스의 장애 기록이나 수정 코드는 사용하지 않는다. 버퍼 계산값과 간단한 표준 라이브러리 예제로 확인할 수 있는 범위만 다룬다.

## PartSize의 0은 버퍼가 없다는 뜻일까

파일 길이를 모르면 `PutObject`에 크기를 `-1`로 전달할 수 있다. 이때 `PutObjectOptions.PartSize`를 생략하면 Go의 제로 값인 `0`이 들어간다. 이 값은 SDK가 part 크기를 계산하도록 맡긴다는 뜻이다.

[minio-go v7.0.97의 `OptimalPartInfo`](https://github.com/minio/minio-go/blob/v7.0.97/api-put-object-common.go)는 크기가 미상일 때 최대 객체 크기를 계산의 기준으로 삼는다. 그 크기를 허용 part 수 안에 나누고 기본 단위로 올림하면 part 하나가 528 MiB가 된다. [크기 미상 업로드 경로](https://github.com/minio/minio-go/blob/v7.0.97/api-put-object.go)는 계산된 크기로 버퍼를 확보한다.

```text
size=-1, PartSize=0
  → SDK가 part 크기를 계산
  → partSize = 553,648,128 bytes = 528 MiB
  → 그 크기의 전송 버퍼를 확보한 뒤 입력을 읽음
```

입력이 실제로 얼마나 짧은지는 버퍼를 정할 때 알 수 없다. 따라서 작은 파일도 이 경로를 타면 큰 버퍼를 요구할 수 있다. 모든 MinIO 업로드나 모든 SDK 버전이 이렇게 동작한다는 뜻은 아니다. **크기 미상 입력, 생략된 PartSize, 특정 버전의 업로드 경로**라는 조건이 함께 있어야 한다.

## 버퍼를 줄이면 메모리 문제도 끝날까

`PartSize`를 명시하면 전송 조각의 크기를 제어할 수 있다. 다만 작은 값이 항상 좋은 것은 아니다. 작은 part는 요청 수를 늘리고, 큰 파일은 허용 part 수와 최대 크기 조건을 함께 만족해야 한다. 병렬 전송 옵션도 살아 있는 버퍼 수에 영향을 준다.

버퍼 한 개의 크기를 B, 요청 하나에서 동시에 유지하는 버퍼 수를 K, 실행 중인 업로드 수를 C라고 하자. **전송 버퍼 항만** 대략 `C × K × B`로 생각할 수 있다. 가상의 예에서 B가 8 MiB, K가 1, C가 4라면 32 MiB다. 이는 RSS 측정값이 아니며 HTTP 파싱, TLS, 다른 객체와 GC 비용은 별도로 더해야 한다.

이 식에서 얻을 수 있는 판단은 두 가지다. B만 줄이고 C를 무제한으로 두면 전체 사용량은 계속 커질 수 있다. 반대로 C를 제한해도 요청을 대기시키기 전에 본문 전체를 읽었다면 대기 중인 요청이 이미 메모리를 사용하고 있다.

```text
처리 자리 확보 → 본문 읽기 → 저장 → 자리 반환
```

이 순서는 애플리케이션이 언제 비싼 할당을 시작할지 제어하는 예다. 인증, 요청 크기 검증, 대기 시간 제한, 취소 처리는 별도로 필요하다. 프록시와 네트워크 버퍼까지 사라지는 것도 아니다.

## 읽기 제한은 초과 검증과 다르다

메모리를 줄이려고 입력을 일정 길이로 제한할 때는 저장 결과도 확인해야 한다. Go의 [`io.LimitReader`](https://pkg.go.dev/io@go1.24.5#LimitReader)는 지정한 길이를 읽고 나면 EOF를 반환한다. 원본에 데이터가 더 있어도 이를 초과 오류로 알리지 않는다.

다음 예제를 실행하면 차이를 볼 수 있다. 실제 업로드 구현을 대신하는 코드는 아니다.

```go
package main

import (
    "fmt"
    "io"
    "strings"
)

func main() {
    data, err := io.ReadAll(io.LimitReader(strings.NewReader("abcdef"), 5))
    if string(data) != "abcde" || err != nil {
        panic("unexpected LimitReader behavior")
    }
    fmt.Printf("data=%q err=%v\n", data, err)
}
```

출력은 `data="abcde" err=<nil>`이다. 성공적으로 읽었지만 원본의 마지막 `f`는 없다. **오류가 없다는 사실과 원본 전체를 보존했다는 사실은 다르다.**

일반적으로 최대 N바이트 입력을 검증하려면 N+1바이트까지 관찰해 초과 여부를 판단할 수 있다. 하지만 데이터를 외부 저장소로 보내는 중이라면 검사가 언제 끝나는지도 중요하다. 초과를 알아내기 전에 저장 완료를 확정하면 검증이 늦다. SDK가 입력을 언제 다시 읽고 언제 multipart 완료를 요청하는지, 실패 시 미완료 업로드를 어떻게 정리하는지까지 확인해야 한다.

## 내 업로드 코드에서는 무엇을 재볼까

먼저 사용하는 SDK 버전과 실제 호출 경로를 고정한다. 길이를 알고 있는 입력과 모르는 입력을 나누고, part 크기와 병렬 전송 설정을 기록한다. 파일 크기만 바꾸면 버퍼 정책의 차이를 놓칠 수 있다.

작은 파일 한 건으로 시작해 동시 실행 수를 늘리면서 heap 할당과 RSS를 따로 측정해 보자. 버퍼를 줄인 뒤에는 메모리뿐 아니라 처리 시간과 저장된 전체 바이트도 비교한다. 실패·취소·크기 초과에서 저장 완료가 잘못 보고되지 않는지도 검사한다.

마지막으로 본문 reader의 호출 횟수를 세는 대역을 넣어 보면 좋다. 처리 자리를 기다리는 동안 읽기 횟수가 늘어난다면, 동시성 제한은 메모리를 쓰기 시작한 뒤에 적용되고 있는 것이다. 그 순서를 확인한 다음 버퍼와 동시 실행 수를 조정해야 한다.
