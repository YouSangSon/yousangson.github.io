여러 파일을 동시에 업로드할 때 MongoDB `WriteConflict`가 발생했다. 파일 자체는 서로 달랐지만, 각 요청이 같은 사용자 문서의 `file_ids`를 수정하고 있었다. 충돌 단위는 파일보다 그 파일들이 참조하는 **공유 문서**였다.

## 락과 트랜잭션은 서로 다른 일을 한다

Redis 분산 락은 같은 락을 사용하는 요청의 진입을 조정한다. MongoDB 트랜잭션은 관련 DB 변경을 함께 커밋하거나 롤백한다. 락이 있다고 트랜잭션이 필요 없어지는 것도, 트랜잭션이 있다고 모든 충돌이 사라지는 것도 아니다.

| 경계 | 다루는 문제 |
| --- | --- |
| 요청 진입 제어 | 동시에 시작할 작업 수와 대기량 |
| 공유 문서 갱신 | 같은 사용자·세션·에이전트 상태의 충돌 |
| MongoDB 트랜잭션 | 관련 DB 변경의 원자성 |
| 외부 객체 저장 | MinIO 저장과 DB 커밋 사이의 실패 |

트랜잭션 재시도는 드라이버가 제공하는 오류 분류와 재시도 계약을 확인해야 한다. 오류 문자열에 `WriteConflict`가 있는지만 보고 중첩 재시도를 추가하면 기존 재시도와 겹칠 수 있다. 콜백이 다시 실행될 수 있으므로 외부 업로드나 알림을 그 안에서 무조건 반복하는 것도 피해야 한다. [MongoDB Go 드라이버 트랜잭션](https://www.mongodb.com/docs/drivers/go/current/crud/transactions/)

## 파일 크기로 나누면 공유 문서도 분리되는가

당시에는 큰 파일의 업로드가 작은 파일을 오래 기다리게 해서 크기별로 락 키를 나눴다. 서로 다른 크기 구간이 병렬로 진행할 수 있지만, 최종적으로 같은 사용자 문서를 갱신한다는 사실은 변하지 않는다.

따라서 파일 크기별 제한은 업로드 자원을 나누는 기준으로 볼 수 있다. 공유 메타데이터를 보호하는 락이나 원자적 갱신의 기준으로 그대로 사용할 수는 없다. 긴 파일 전송과 짧은 공유 문서 갱신 구간을 나누어 설계해야 한다. [락 세분화의 한계를 다시 본 글](/posts/file-upload-lock-granularity-and-retry/)

## 재시도에는 종료 조건이 필요하다

서버에서 락 획득을 재시도하면 일부 충돌을 흡수할 수 있다. 그래도 최대 대기 시간과 요청 취소를 처리하고, 최종 실패는 호출자에게 전달해야 한다. 응답이 끊긴 경우 재요청이 중복 업로드가 되지 않도록 요청 식별자와 멱등성도 확인한다.

Redis 장애 때 락 없이 진행해도 되는지는 남은 저장소 제약이 데이터 불변식을 지키는지에 달려 있다. 단순히 “개발 환경이면 허용”하는 예시는 동시성 보장을 검증하지 못하므로 제거했다. 락이 정확성의 필수 조건인 경로에서는 획득 실패를 성공으로 바꾸지 않는다.

## MinIO 저장 뒤 DB가 실패하면

객체 저장과 MongoDB 커밋은 하나의 트랜잭션이 아니다. 메타데이터 기록이 실패하면 업로드 객체를 정리하거나 정리할 작업을 내구성 있게 남겨야 한다. 정리 기록 저장까지 실패했다면 로그 한 줄만으로 복구를 보장할 수 없다.

재시도 사이에 같은 객체 키를 덮어쓸 수 있다면 늦게 실행된 정리가 새 파일을 삭제할 수도 있다. [문서 버전의 정체성을 파이프라인 끝까지 유지하는 방법](/posts/immutable-versions-through-rag-pipeline/)에서는 업로드·파싱·임베딩·삭제가 같은 버전을 가리키도록 만드는 경계를 다룬다.

## 후속 장애: 락이 메모리 사용량을 제한하지는 않는다

최근 MinIO 사례에서는 작은 파일인데도 SDK가 큰 버퍼를 먼저 할당했다. DB 충돌을 막는 락과 별개로, **본문을 읽기 전에** 진입을 제한하고 요청별 버퍼 크기를 정해야 했다. [작은 파일 업로드가 528 MiB를 쓰던 이유](/posts/upload-memory-admission-before-body/)

확인할 때는 같은 사용자에게 서로 다른 크기의 파일 두 개를 동시에 올려 보자. 데이터 정합성, 대기 시간, 메모리 사용량을 각각 봐야 한다. 성공 응답만 확인하면 세 문제 중 나머지 둘을 놓칠 수 있다.

기존 글의 성공률·지연 시간 표는 부하 조건과 원시 측정 결과가 함께 남아 있지 않아 제거했다. 이 글의 보완은 설계 경계를 바로잡은 것이며 새 성능 측정 결과를 제시하는 것은 아니다.
