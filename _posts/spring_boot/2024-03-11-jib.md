Java 코드 한 줄을 고쳤을 뿐인데 큰 컨테이너 이미지를 다시 보내야 한다면, 무엇이 함께 묶여 있는지 살펴볼 만하다. 자주 바뀌는 애플리케이션 코드와 거의 바뀌지 않는 의존성을 한 덩어리로 다루면 작은 수정의 영향도 커진다.

[Jib](https://github.com/GoogleContainerTools/jib)은 Java 애플리케이션의 의존성과 클래스를 서로 다른 이미지 레이어로 구성한다. 핵심은 **변경 주기가 다른 것을 나누어, 바뀌지 않은 부분을 재사용하는 것**이다. Docker 데몬 없이 Maven·Gradle에서 이미지를 만드는 기능도 제공한다.

## 어떤 변경이 어느 레이어에 영향을 줄까

| 바꾼 입력 | 확인할 부분 |
| --- | --- |
| 애플리케이션 클래스 | 의존성 레이어를 다시 만들거나 보내는가? |
| 라이브러리 버전 | 의존성 레이어가 실제로 갱신됐는가? |
| 베이스 이미지 | 애플리케이션이 같아도 이미지 입력이 달라졌는가? |

이 표는 실험할 조건이다. 캐시가 비어 있는 첫 빌드와 이미 같은 레이어를 가진 환경은 결과가 다를 수 있다. 빌드 시간, 전송한 바이트, 최종 이미지 크기도 다른 지표다. 레이어를 재사용해 업로드가 빨라졌다고 이미지 자체가 작아진 것은 아니다.

## 빌더를 바꿔도 남는 설정

베이스 이미지에는 필요한 Java 런타임과 OS 라이브러리가 있어야 한다. 실행 환경의 CPU 아키텍처도 맞아야 한다. Jib을 쓴다는 사실만으로 호환성이나 취약점 관리가 끝나지는 않는다. 레지스트리 주소와 인증 정보는 공개 예제에 넣지 않고 프로젝트의 배포 설정에서 관리한다.

또한 같은 태그가 언제나 같은 베이스 이미지를 뜻하는 것은 아니다. 재현성을 확인할 때는 소스뿐 아니라 의존성, 베이스 이미지와 빌드 설정도 비교해야 한다. Jib은 같은 내용으로 같은 이미지를 만드는 것을 목표로 하지만, 입력이 바뀐 빌드까지 같게 만드는 도구는 아니다.

## 두 번째 빌드에서 확인해 보자

프로젝트가 검증한 Jib 플러그인과 Java 런타임 조합을 준비한 뒤, 같은 입력으로 두 번 빌드해 캐시 재사용을 확인한다. 다음에는 클래스 하나만 바꾸고, 그다음에는 의존성 하나만 바꾼다. 각 경우에 바뀐 레이어와 전송량을 비교하면 분리의 효과를 설명할 수 있다. 이 글은 그 비교 방법을 제안하며 측정한 속도 향상 수치를 제시하지는 않는다.

실제 플러그인 설정과 빌드 대상별 명령은 [Jib Gradle 문서](https://github.com/GoogleContainerTools/jib/tree/master/jib-gradle-plugin)를 기준으로 맞춘다. 도구 이름을 고르기 전에, 자주 바뀌는 입력 때문에 변하지 않은 데이터까지 다시 처리하고 있는지 먼저 확인해 보자.
