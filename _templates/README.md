# 블로그 글 템플릿

이 저장소의 글쓰기 기준 파일이다. `technical-blog-publish`는 초안을 쓰거나 기존 글을 크게 고치기 전에 이 문서와 해당 유형의 템플릿을 읽는다. 템플릿 자체는 발행하지 않는다. 완성한 글만 현재 체크아웃의 게시 규칙에 맞게 `_posts/`에 저장한다.

## 어떤 틀을 고를까

| 독자에게 남길 것 | 템플릿 | 시작하기 좋은 소재 |
| --- | --- | --- |
| 작업 중 이해하게 된 원리와 판단 기준 | [학습·기술 설명](learning.md) | 버퍼와 동시성, 인덱스, 스케줄링, 파싱 |
| 증상에서 원인을 찾고 고친 근거 | [문제 해결·최적화](problem-solving.md) | 메모리 증가, 경쟁 조건, 느린 쿼리 |
| 직접 실행하며 익히는 한 가지 기술 | [실습](tutorial.md) | 작은 파서 만들기, 검색 평가 실습 |
| 연구의 기여와 성립 조건 | [논문 리뷰](paper-review.md) | 알고리즘, 시스템, 서베이, 벤치마크 |
| 프로젝트의 동작과 채택 판단 | [오픈소스 리뷰](opensource-review.md) | 라이브러리, 엔진, 학습 자료 모음 |

한 글의 주된 목적을 고른다. 학습 글에 짧은 실험을 넣을 수 있지만 설치 설명이 원리 설명을 밀어내지 않도록 한다. 아래 절 제목은 초안용 안내다. 주제에 맞게 고치고 불필요한 절은 합친다. 같은 도입·마무리 문장을 모든 글에 반복하지 않는다.

## 공통 편집 기준

**일관성은 독자가 받는 설명과 근거에 둔다.** 구체적인 현상에서 시작해, 원리를 설명하고, 독자가 따라갈 수 있는 사례로 확인한 다음 적용 조건을 밝힌다. 분량이나 소제목 개수를 깊이의 기준으로 삼지 않는다.

- 도입: 독자가 아는 상황과 이번 글에서 풀 문제를 짧게 연결한다. 개인 경험은 확인된 사실일 때만 쓴다. 개념 공부를 장애 대응담으로 꾸미지 않는다.
- 설명: 한 문단에서 한 생각을 발전시킨다. 새 용어·기호·단위를 사용하기 전에 정의한다. `P0` 같은 내부 표기 대신 우선 “실패한 작업이 있는 파티션”처럼 역할을 설명한다.
- 사례: 핵심 코드, 입력, 출력과 그 해석을 본문에 둔다. 긴 실행 환경이나 완성본 다운로드는 보충 자료다. 링크를 열어야 원리를 알 수 있다면 본문이 덜 쓰인 것이다.
- 깊이: 결론으로 넘어가는 추론을 생략하지 않는다. 작은 계산, 실행 순서, 대조 실험 중 적합한 것으로 이유를 보이고, 조건 하나가 달라졌을 때 결론이 유지되는지도 설명한다.
- 근거: 원저자의 결과, 직접 실행한 결과, 소스에서 추론한 동작을 구별한다. 실행하지 않았다면 관측한 출력처럼 쓰지 않는다. 측정에는 버전·입력·범위·비교 조건을 붙인다. Go 예제는 사용자 기준 1.24.5와 실제 실행 환경을 대조한다.
- 마무리: 독자가 다음 문제에서 사용할 판단 기준으로 끝낸다. 매번 퀴즈·체크리스트·“핵심은” 문장을 붙이지 않는다.
- 공개 범위: 업무에서 배운 일반 원리를 독립 예제로 설명한다. 회사 코드의 이름만 바꿔 옮기지 않는다. 내부 정책·토폴로지·지표·로그가 노출되지 않도록 본문과 자산을 함께 검토한다. 가상 상황은 가상이라고 표시한다.

## 코드·표·그림의 자리

코드 앞에는 무엇을 확인할지, 뒤에는 어떤 줄과 출력이 결론을 뒷받침하는지 적는다. 틀린 예시는 틀렸다고 소개하고 필요한 수정도 가까이에 보여 준다. 코드 캡처 대신 복사 가능한 코드 블록을 쓴다.

그림은 캡션의 설명 목적부터 정한다. 관계에는 구조도, 순서에는 흐름도, 조건별 값에는 표나 그래프를 고른다. **문장으로 읽는 법 → 그림/표 → 결과 해석**을 같은 절 안에 배치한다. 장식용 그림이나 일정 문단마다 그림을 넣는 규칙은 두지 않는다.

논문의 핵심 그림·표는 재사용 조건을 확인한 뒤 필요한 부분을 본문에 삽입한다. 작은 글씨가 많은 표는 결정적인 값을 한국어 표로도 풀고 생략·재계산 여부를 밝힌다. 재사용할 수 없으면 수치의 출처를 적은 자체 표나 직접 그린 설명도를 쓴다. 그림 캡션에는 원문 판본, 그림/표 번호, 출처, 필요한 권리 표시와 편집 여부를 적는다. 원문 링크는 계속 제공한다.

새 다이어그램은 사이트의 색상·글꼴·밝음/어두움 테마를 따른다. 실제 본문 폭에서 모바일 글자 크기와 잘림을 확인한다. 대체 설명을 두고, 색상만으로 의미를 구분하지 않는다. “그림 크게 보기” 링크는 본문 삽입을 대신하지 않는다.

## 초안에서 발행본으로

템플릿의 HTML 주석은 작성 지침이며 최종 글에서 삭제한다. Frontmatter는 현재 체크아웃의 최근 글과 스키마에서 가져온다. 제목·설명·날짜·카테고리·태그를 채우고 기존 글의 URL을 함부로 바꾸지 않는다. 오래된 체크아웃의 사이트 기술을 최신 발행본에 그대로 적용하지 않는다.

발행 전에는 본문의 용어와 논리, 공개 적합성, 출처와 수치를 검토한다. 필수 설명이 외부 링크에만 남지 않았는지 확인한다. 본문을 렌더링해 문장·기호·표·코드·그림이 보존되는지 비교하고, 현재 저장소가 요구하는 검사를 실행한다. 조사 범위 목록과 검증 로그는 공개 글에 넣지 않는다.

## 설계에 참고한 글

2026-09-29 원문 확인. 아래는 각 저자의 글에서 관찰한 구성과 이 블로그에 적용할 편집 선택이다. 모든 글에 같은 구조가 최선이라는 실험적 결론은 아니다.

| 출처 | 관찰한 구성 | 이 템플릿에 적용 |
| --- | --- | --- |
| [Julia Evans — Write good examples by starting with real code](https://jvns.ca/blog/2021/07/08/writing-great-examples/) | 현실적인 작업을 작은 독립 예제로 줄여 개념의 필요성을 보여 준다. | 작업에서 질문을 얻고 공개 가능한 독립 예제를 만든다. 회사 소스 복사를 허용하는 근거로 삼지 않는다. |
| [Diátaxis — Explanation](https://diataxis.fr/explanation/) · [Tutorials](https://diataxis.fr/tutorials/) | 이해를 위한 맥락·대안 설명과 행동을 통해 배우는 경로를 구분한다. | 학습·기술 설명과 실습을 별도 틀로 둔다. 문서 체계 전체를 블로그에 강제하지 않는다. |
| [Google Technical Writing — Illustrating](https://developers.google.com/tech-writing/two/illustrations) | 캡션의 목적을 먼저 정하고 복잡한 그림을 나누며 시선을 안내한다. | 그림을 넣을 자리와 읽는 법을 함께 작성한다. |
| [Wattenberg·Viégas·Johnson — How to Use t-SNE Effectively](https://distill.pub/2016/misread-tsne/) | 작은 사례의 조건을 바꾸며 시각화에서 읽을 수 있는 것과 없는 것을 설명한다. | 대표 사례에 조건을 바꾼 대조 사례를 붙인다. 모든 글에 인터랙티브 구현을 요구하지 않는다. |
| [Eli Bendersky — Common pitfalls in Go benchmarking](https://eli.thegreenplace.net/2023/common-pitfalls-in-go-benchmarking/) | 잘못 측정한 코드, 측정 결과, 원인과 수정 코드를 이어 보여 준다. | 최적화 글에 측정 범위와 대조 조건을 둔다. 과거 코드의 현재 유효성은 별도로 확인한다. |

이 자료들은 설명 구조를 참고하기 위한 것이다. 문장·이미지·성과 수치를 가져와 자신의 경험으로 쓰지 않는다. Medium처럼 여러 작성자가 모인 플랫폼의 공통 외형보다 개별 글의 설명과 근거를 기준으로 골랐다.
